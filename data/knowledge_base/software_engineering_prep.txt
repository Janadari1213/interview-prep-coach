=== SOFTWARE ENGINEERING INTERVIEW KNOWLEDGE BASE (20+ DEMO QUESTIONS & MODEL ANSWERS) ===

Q1: What is the difference between an Abstract Class and an Interface in OOP?
Model Answer: An Abstract Class represents an 'is-a' relationship and serves as a base class with shared state (fields/variables) and concrete method implementations. An Interface defines a 'can-do' behavioral contract with public method signatures. Subclasses support single inheritance for abstract classes, but can implement multiple interfaces.
Evaluation Criteria: Single vs. multiple inheritance rules, state vs. stateless contract, and design choice justification.
Coaching Tips: Structure by comparing Purpose ('is-a' vs 'can-do'), State (instance variables vs constants), and Inheritance.

Q2: How do you solve the Two Sum problem efficiently in O(n) time complexity?
Model Answer: Use a Hash Map (dictionary) to store each number's complement (target - num) as you iterate through the array. For each element `num` at index `i`, check if `target - num` exists in the hash map. If found, return `[map[complement], i]`. Otherwise, record `map[num] = i`.
Evaluation Criteria: Hash table lookup O(1) efficiency, O(n) single pass time complexity vs O(n^2) brute force.
Coaching Tips: Briefly state brute force O(n^2), then present the Hash Map O(n) optimization with time/space complexity analysis.

Q3: Explain SOLID principles in Object-Oriented Software Design.
Model Answer: SOLID stands for Single Responsibility (one reason to change), Open/Closed (open for extension, closed for modification), Liskov Substitution (subtypes must be substitutable for base types), Interface Segregation (fine-grained interfaces), and Dependency Inversion (depend on abstractions, not concretions).
Evaluation Criteria: Explaining all 5 acronym letters accurately with real-world refactoring examples.
Coaching Tips: Use concise single-sentence definitions for each letter, then provide a code refactoring example for Dependency Inversion.

Q4: What is the difference between Process and Thread in Operating Systems?
Model Answer: A Process is an independent execution unit with its own virtual address space, memory, and system resources. A Thread is a lightweight segment of execution within a process that shares memory and resources with peer threads, reducing context switching overhead.
Evaluation Criteria: Memory isolation, context switching cost, and concurrency vs multithreading risks (race conditions).
Coaching Tips: Highlight memory sharing (shared heap vs isolated stack) and IPC overhead.

Q5: How does Garbage Collection work in Java / Python?
Model Answer: Garbage collection automatically reclaims memory occupied by objects that are no longer reachable from root references (stack frames, static fields). It uses algorithms like Mark-and-Sweep, Generational Collection (Young/Old gen), and Reference Counting with cycle detection.
Evaluation Criteria: Understanding unreachable object graphs, mark-sweep phases, and generational hypothesis.
Coaching Tips: Explain why generational collection separates short-lived objects from long-lived objects.

Q6: Explain RESTful API design principles and HTTP status codes.
Model Answer: REST relies on stateless client-server communication using HTTP verbs (GET, POST, PUT, DELETE, PATCH) over URI resource paths. Status codes indicate outcome: 200 OK, 201 Created, 400 Bad Request, 401 Unauthorized, 403 Forbidden, 404 Not Found, 500 Internal Server Error.
Evaluation Criteria: Resource-oriented URI naming, idempotency of HTTP methods, and appropriate status code usage.
Coaching Tips: Emphasize idempotency (PUT vs POST) and proper URI plural nouns (`/users/123`).

Q7: What is Database Normalization and why is 3NF important?
Model Answer: Normalization reduces data redundancy and prevents update anomalies by organizing tables into normal forms. First Normal Form (1NF) eliminates duplicate columns; 2NF removes partial key dependencies; 3NF removes transitive dependencies where non-key attributes depend on other non-key attributes.
Evaluation Criteria: Identifying anomalies (insertion, deletion, update) and defining functional dependencies.
Coaching Tips: Use a simple Employee-Department table example to demonstrate 3NF decomposition.

Q8: Compare SQL (Relational) vs NoSQL (Document/Key-Value) Databases.
Model Answer: SQL databases (PostgreSQL, MySQL) enforce ACID transactions, structured schemas, and relational joins, ideal for complex transactions. NoSQL databases (MongoDB, DynamoDB) offer dynamic schemas, horizontal scaling (sharding), and eventual consistency (BASE), ideal for high throughput unstructured data.
Evaluation Criteria: CAP theorem trade-offs, ACID vs BASE consistency, and scaling strategies.
Coaching Tips: Frame the choice around data access patterns and scaling needs rather than popularity.

Q9: What is Microservices Architecture and how does it compare to Monolithic?
Model Answer: A Monolith packages all business domains into a single codebase and deployment unit. Microservices decompose functionality into independently deployable, loosely coupled services communicating via APIs (gRPC/REST) or message queues (Kafka), enabling polyglot stacks and independent scaling.
Evaluation Criteria: Domain-driven design, service boundaries, distributed transaction management (Saga pattern), and operational overhead.
Coaching Tips: Discuss operational complexity (CI/CD, service mesh) alongside microservice benefits.

Q10: Explain the CAP Theorem in Distributed Systems.
Model Answer: CAP theorem states that a distributed data store can simultaneously provide at most two of three guarantees: Consistency (every read receives the most recent write), Availability (every request receives a non-error response), and Partition Tolerance (system operates despite network package drops).
Evaluation Criteria: Understanding that Partition Tolerance (P) is mandatory in real networks, leaving choices between CP and AP.
Coaching Tips: Give concrete examples: HBase/MongoDB (CP) vs Cassandra/DynamoDB (AP).

Q11: What is Dependency Injection and how does it promote testability?
Model Answer: Dependency Injection (DI) is an implementation of Dependency Inversion where an object's dependencies are provided (injected) from the outside rather than created internally. This allows injecting mock or fake implementations during unit testing.
Evaluation Criteria: Decoupling components, constructor injection vs field injection, and test mock creation.
Coaching Tips: Contrast tight coupling (`new Service()`) with loose coupling constructor injection.

Q12: How do Indexes work in SQL Databases (B-Trees)?
Model Answer: SQL indexes use B-Tree (or B+ Tree) data structures to maintain sorted key-pointer pairs, reducing query search time from O(n) full table scans to O(log n) logarithmic lookups. However, indexes add overhead to WRITE (INSERT/UPDATE/DELETE) operations.
Evaluation Criteria: B-Tree structure, composite index column order, and write penalty trade-offs.
Coaching Tips: Mention index selectivity and explain why indexing low-cardinality boolean columns is inefficient.

Q13: Explain CI/CD Pipelines and Automated Testing Strategies.
Model Answer: CI/CD automates code validation, build, testing, and deployment. The testing pyramid includes Unit Tests (fast, isolated logic), Integration Tests (database/API interactions), and End-to-End Tests (full application user journeys).
Evaluation Criteria: Test automation coverage, pipeline feedback speed, and deployment safety (Canary/Blue-Green).
Coaching Tips: Emphasize pushing bug detection to early pipeline stages (unit testing).

Q14: How do WebSockets differ from HTTP Polling?
Model Answer: HTTP Polling requires the client to repeatedly send HTTP requests to check for new data. WebSockets establish a single persistent, full-duplex TCP connection allowing bi-directional real-time data streaming between client and server with minimal header overhead.
Evaluation Criteria: Duplex communication, socket connection overhead, and scaling WebSocket servers (sticky sessions/Redis pub-sub).
Coaching Tips: Contrast short polling, long polling (Comet), and WebSockets.

Q15: What is Docker Containerization and how does it differ from Virtual Machines?
Model Answer: VMs virtualize full hardware hardware stacks and run complete guest OS instances on a hypervisor. Docker containers virtualize the operating system kernel, sharing the host OS kernel to run lightweight, isolated application user-spaces with sub-second startup times.
Evaluation Criteria: Resource overhead, isolation guarantees, kernel sharing, and image layer caching.
Coaching Tips: Highlight portability, startup speed, and resource efficiency.

Q16: How do you handle Concurrency and Thread Safety (Locks, Semaphores, Mutex)?
Model Answer: Thread safety prevents race conditions when concurrent threads access shared mutable state. Synchronization tools include Mutex (mutual exclusion lock for single thread access), Semaphore (permits access up to N concurrent threads), and Atomic variables (hardware-assisted non-blocking updates).
Evaluation Criteria: Race conditions, deadlocks, lock starvation, and atomic operations.
Coaching Tips: Explain deadlock prevention (locking ordering, try-lock timeouts).

Q17: Explain the STAR Method for Behavioral Software Engineering Questions.
Model Answer: STAR structures scenario answers into Situation (context/background), Task (your specific responsibility), Action (technical decisions and actions YOU personally executed), and Result (quantifiable outcomes, metrics, and key learnings).
Evaluation Criteria: Structured storytelling, individual ownership, technical depth, and metric-driven results.
Coaching Tips: Dedicate 60% of response time to Action and Result steps.

Q18: How do you approach System Design for a Scalable URL Shortener (Bit.ly)?
Model Answer: 1. Estimate scale (reads vs writes, storage requirement). 2. Define API endpoints (`encode`, `decode`). 3. Key Generation Algorithm (Base62 encoding of auto-incrementing ID or MD5 hash prefix). 4. Data storage (NoSQL Key-Value store) + Redis caching layer for hot URLs. 5. Load balancing and database sharding.
Evaluation Criteria: Requirements estimation, hash encoding logic, caching strategy, and database scaling.
Coaching Tips: Structure system design answers logically: Requirements -> Scale Estimation -> API -> DB Schema -> High-Level Design -> Deep Dives.

Q19: What is Event-Driven Architecture (Pub/Sub with Kafka/RabbitMQ)?
Model Answer: Event-Driven Architecture decouples microservices by publishing state change events to a central message broker. Event producers publish messages to topics without knowing consumers; consumers subscribe to topics to process events asynchronously.
Evaluation Criteria: Asynchronous decoupling, message delivery guarantees (at-least-once, exactly-once), and dead letter queues.
Coaching Tips: Highlight fault tolerance, scalability, and handling consumer lag.

Q20: How do you design and implement secure authentication (JWT vs Session Cookies)?
Model Answer: Session Cookies store session IDs on the server (stateful database/Redis lookups) with httpOnly, secure, sameSite flags. JWT (JSON Web Tokens) are stateless, cryptographically signed tokens containing user claims, validated by servers without DB lookups.
Evaluation Criteria: Stateful vs stateless authentication, token revocation challenges, CSRF vs XSS vulnerability mitigations.
Coaching Tips: Mention token expiration, refresh token rotation, and secure cookie flags.
